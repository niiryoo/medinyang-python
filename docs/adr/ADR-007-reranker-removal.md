# ADR-007: 의도 필터 도입 후 재순위화 기본 비활성

**ADR-003을 부분 대체.** 재순위화 모델 선택(bge-reranker-base)은 유효하나, 사용 여부 판단이 바뀌었다.

## 관측

ADR-003에서 재순위화를 채택할 때 근거는 dense 후보 위에서의 측정이었다.

| E4 − E2 | 차이 | 95% CI | 판정 |
|---|---|---|---|
| Precision@5 | +3.00%p | [+0.28, +5.72] | 유의 |
| 의도 일치@5 | +1.36%p | [-1.39, +4.12] | 구분불가 |
| 질환 일치@5 | +2.45%p | [+0.94, +3.97] | 유의 |

이득이 질환 축에서만 나왔고 CI 하한도 +0.28로 아슬아슬했다. ADR-006에서 의도 필터를
도입하면서 "후보가 의도로 균질해지면 리랭커가 볼 변별 축이 하나 줄어든다"고 적어뒀고,
재측정이 필요했다.

## 원인

재순위화는 검색기가 놓친 순위를 교차 인코더로 바로잡는 단계다. 그런데 의도 필터가
상위 단계에서 의도 오류를 이미 걷어내면, 리랭커가 고칠 것이 질환 오류만 남는다.

즉 **두 장치가 같은 오류의 일부를 중복해서 다룬다.** 상위 장치가 더 잘하면
하위 장치의 한계 기여가 줄어든다.

## 고려한 대안

| 안 | 장점 | 단점 |
|---|---|---|
| (a) 재순위화 유지 | 논문 구성 그대로 | GPU 없으면 질의당 14초. 이득은 구분불가 |
| (b) 코드 삭제 | 단순 | GPU 환경에서는 거의 무료인 선택지를 없앰. 재현 불가 |
| (c) **설정으로 남기되 기본 비활성** | 기본값이 CPU 서빙에 맞고, GPU면 켤 수 있음 | 경로가 둘 |
| (d) 후보 수를 늘려 리랭커에 여지를 줌 | 이득 회복 가능 | 미측정. 비용은 더 커짐 |

## 결정

(c). `config.USE_RERANKER = False`가 기본이고, `USE_RERANKER=1`로 켤 수 있다.

**기본값을 끄는 쪽으로 정한 근거는 CPU 서빙 전제다.** 이 프로젝트에 GPU 서빙 인프라가
없고, CPU에서 질의당 14초는 대화형 서비스로 쓸 수 없다. 반대로 GPU가 있다면
0.44초에 +0.82%p이므로 켜는 편이 합리적이다 — 다만 그 이득도 구분불가라 필수는 아니다.

즉 이 결정은 "재순위화가 쓸모없다"가 아니라 **"주어진 인프라에서 값어치가 안 나온다"**다.

## 검증

골든셋 220건, 의도 필터 적용 후 대응표본 비교 (E9 − E8).

| 지표 | 차이 | 95% CI | 판정 |
|---|---|---|---|
| Precision@5 | +0.82%p | [-0.62, +2.25] | 구분불가 |
| Precision@10 | +0.64%p | [-0.17, +1.44] | 구분불가 |
| 의도 일치@5 | **+0.00%p** | [0.00, 0.00] | 구분불가 |
| 질환 일치@5 | +0.82%p | [-0.64, +2.28] | 구분불가 |

의도 일치율 차이가 **정확히 0.00%p**다. 후보 20건이 전부 같은 의도이므로 재순위화가
이 축을 바꾸는 것이 수학적으로 불가능하다. ADR-006의 예측이 그대로 확인됐다.

질환 축 기여는 ADR-003의 +2.45%p(유의)에서 +0.82%p(구분불가)로 줄었다.

### 비용

**하드웨어에 따라 결론이 갈린다.**

| 재순위화 220건 | 질의당 |
|---|---|
| GPU (Colab T4) | 97.4s | 0.44s |
| CPU (16코어) | 약 3,095s | 14.1s |

약 32배 차이다. E9 측정은 Colab GPU를 배정받지 못해 CPU로 돌린 값이므로,
E8(148.3s)과 E9(3,243.0s)의 21.9배는 **리랭커의 속성이 아니라 실행 환경의 결과**다.

GPU가 있으면 질의당 0.44초로 사실상 무료다. CPU 서빙이면 14초가 붙어
대화형 서비스로 쓸 수 없다. 모델 가중치 1.1GB는 양쪽 공통이다.

## 트레이드오프

**`구분불가`는 "효과가 없다"가 아니다.** MDE가 2.05%p이므로, 실제로 +2%p 정도의
이득이 있는데 220건으로 못 본 것일 수 있다. CI 상한도 +2.25%p로 열려 있다.

즉 이 결정은 "효과가 없어서"가 아니라 **"있다 해도 2%p 미만인데, CPU 서빙에서
질의당 14초를 지불해야 해서"**다. 골든셋을 232건으로만 늘려도 2%p를 판별할 수 있으므로,
판단을 뒤집고 싶다면 표본을 늘려 재측정하는 것이 정직한 경로다.

**GPU 환경이라면 이 결정은 성립하지 않는다.** 0.44초에 +0.82%p면 켜는 쪽이 낫다.
기본값이 인프라 전제에 묶여 있다는 점을 명시해 둔다.

그리고 이 결정으로 **논문의 핵심 구성인 retrieve-then-rerank에서 rerank 단계가 빠진다.**
논문 재현이라는 관점에서는 이탈이다. 다만 논문 설정(E1) 대비 최종(E8)이
Precision@5 +28.45%p이므로, 재현이 아니라 개선이 목적이라면 감수할 이탈이다.
`USE_RERANKER=1`로 언제든 논문 구성을 복원할 수 있게 남겨둔 이유이기도 하다.

## 2차 효과

재순위화가 빠지면서 **폴백 판정의 근거로 쓸 점수가 사라진다.** ADR-004에서 이미
그 점수로는 게이팅이 성립하지 않는다고 결론 냈으므로(AUC 0.586) 실질적 손실은 없다.

대신 ADR-006에서 확인한 **의도 분류 신뢰도(AUC 0.758)** 가 더 나은 신호로 남아 있다.
검색 필터 해제에 쓰는 것은 손해였지만, 폴백 판정에 쓰는 것은 별개 문제이며 아직 재지 않았다.
`RELEVANCE_THRESHOLD`의 후속 검토는 이쪽으로 간다.

또한 CPU 서빙이 현실적인 선택지가 됐다. 질의당 25초가 넘어가면 대화형 서비스로 쓸 수 없다.

## 재현

```bash
python -m scripts.evaluate --index db_3small --intent-filter --out docs/g220-E8.json
python -m scripts.evaluate --index db_3small --intent-filter --rerank --out docs/g220-E9.json
python -m scripts.compare docs/g220-E9.json docs/g220-E8.json
```
